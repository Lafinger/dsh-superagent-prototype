# 需求：同一 PR 后续推送返工时飞书回帖

> 版本 v1.0 ｜ 状态：未实现（待办） ｜ 更新：2026-11-27 ｜ 优先级：中

## 1. 背景

当前交付链路里，**首次提交结果 PR** 已经能自动衔接：PR 正文写 `归属计划 #N` 时，"成果直通"会把该 PR 挂到计划的工单上，协调者随即在飞书话题里回帖并 @ 下一岗位。

但**同一 PR 的后续推送（返工）** 不会产生任何飞书消息。评审意见通常通过"改完再推一次"来闭环，此时：

- 需求方在飞书里看不到"已收到返工版本"；
- 下一岗位（实施/审阅）不知道该以哪个提交为准；
- 判断是否交付只能反复去 GitHub 看。

## 2. 目标

> 任何人在**同一个 PR** 上推送新提交（含追加 commit 与 force push）后，**1 分钟内**在工单原始的飞书话题里出现一条通知，说明"这是返工版本 + 是哪个提交"。

## 3. 术语

| 术语 | 含义 |
|---|---|
| 返工 | 同一个 PR 的 head 提交发生变化（不是新 PR）|
| head sha | PR 当前最新提交的完整 SHA |
| 工单话题 | 该需求最初在飞书里发起的那条话题（`ticket.channels` 中 `source = feishu`）|
| 成果直通 | PR 正文/评论带 `归属计划 #N` 时自动挂到计划工单的机制（已实现）|

## 4. 现状（本次改造前）

| 能力 | 状态 | 说明 |
|---|---|---|
| 新 PR → 挂工单 → 协调者回帖 | ✅ 已实现 | 触发器 ID 为 `github-issue:<PR号>` |
| PR 评论（带计划号）→ 挂工单 | ✅ 已实现 | 触发器 ID 为 `github-comment:<评论id>` |
| **同一 PR 推新提交 → 飞书通知** | ❌ **未实现** | 触发器 ID 按 PR 号固定，推送被当作重复事件丢弃 |
| 协调者主动催办/结果回帖 | ✅ 已实现 | 但**不保证**针对返工推送发言 |

## 5. 功能需求

### FR-1 检测推送

- 轮询 `GET /repos/{owner}/{repo}/pulls?state=all&sort=updated&direction=desc`，读取每个 PR 的 `head.sha`；
- 与本地记录的基线比较（`github-pull-head:<PR号>`），**sha 变化即视为一次推送**；
- 首次见到某 PR 只建立基线，不通知；
- PR 已 `closed`/`merged` 后不再通知（只更新基线）。

### FR-2 发出通知

- 目标频道：工单的飞书话题（`ticket.channels` 中 `source = feishu`，`address.chatId` + `address.messageId`）；
- 通知内容至少包含：PR 号、短 sha（7 位）、新提交标题、"返工版本"字样；
- 示例文案：

  ```
  PR #9 有新提交（583ba58「文档：追加重置设计 v1.5 复核」），返工版本已记录。
  ```

### FR-3 去重与节流

- 同一 `(工单, sha)` 只通知一次；
- 同一工单 **60 秒**内最多一条（避免连续 force push 刷屏）；
- 被节流跳过的那次**不更新基线**，以便下一个轮询补发（保证不漏）。

### FR-4 与协调者的关系

- 通知由 **host 直接发出**，不依赖协调者是否发言；
- 协调者若也回帖，允许并存（不做强行合并）；
- 不得影响"成果直通"的挂单行为，也不得阻塞 attach。

### FR-5 可观测性

- 通知失败不得静默：写入应用日志（`[push-notice] …`），日志中能看到 PR 号、sha、失败原因；
- 通知成功后可查询到对应回执（outbox receipt 状态 `sent`）。

## 6. 非功能需求

| 项 | 要求 |
|---|---|
| 延迟 | 推送后 ≤ 1 分钟（受轮询周期约束）|
| 噪音 | 单 PR 每分钟最多 1 条；正确跳过基线建立 |
| 兼容 | 不影响现有触发器 ID 规则、不影响成果直通 |
| 成本 | 每轮 1 次 `pulls` 列表调用；仅在检测到变化时多 1 次 `commits/{sha}` 取提交标题 |
| 配置 | 无独立开关（常开）；如需关闭，走既有设置页 |

## 7. 验收标准

1. 对同一 PR 追加一个 commit → ≤ 1 分钟内，工单飞书话题出现上述通知，且 sha 正确；
2. 对同一 PR 做 force push → 同样出现通知（sha 为新值）；
3. 同一 sha 重复轮询 → **不产生**第二条；
4. 连续两次推送（间隔 < 60 秒）→ 只出现一条，且第二次在下一窗口补发；
5. 新 PR 首次被轮询到 → **不通知**（仅建立基线）；
6. 已合并/关闭的 PR 再推送 → **不通知**；
7. 通知失败时：日志有 `[push-notice]` 记录，且 attach 与协调者流程不受影响；
8. 回归：现有"成果直通"（新 PR 挂单 + 协调者回帖）行为不变。

## 8. 已知技术风险（来自上一次失败尝试）

> 本节是必读：同一目标曾实现三次均失败并回退（commit `8ed5800`）。

| 尝试 | 做法 | 失败原因 |
|---|---|---|
| 1 | 在 `engine.attach(..., note)` 的备注里要求回帖 | `Tickets.attach` 仅在输入**未投递**时更新 note，投递后丢弃 → 模型看不到 |
| 2 | 把命令写进**触发器正文** + 提示词例外（`communication.md`、`SKILL.md`）| 被 `dispatch.md`「不重复已沟通的里程碑」压制，模型仍判断"无需动作" |
| 3 | 直接改最强抑制点（`dispatch.md` L22、`orchestrator.md` L12）并重置协调者会话 | 模型口径变为"继续等待，不做催促"，仍不发言 |
| 4 | host 在 `Runtime.receive` 里直接发通知（`outbox.send`）| 触发器/attach 均正常，但通知与诊断键都未落库；当时容器已半死（`ps`/`exec` 挂起），日志也未落到 `.artifacts` |

**结论：**

- 不要再依赖**提示词**驱动"是否发言"，这是模型可裁量的决策，四次注入都不稳定；
- 通知必须由 **host 代码**发出；
- 上次未定位的最后一环是"`Runtime.receive` 内的写入不可观测"，因此本次建议**换一层实现**（见第 9 节），并**先解决日志可见性**。

## 9. 备选实现方案

| 方案 | 位置 | 优点 | 风险 |
|---|---|---|---|
| **A（推荐）** | `core/engine.ts` 的 `attach()` 内，检测 `trigger.meta.kind === 'push'` 后直接 `outbox.send(...)` | 与已证明可用的 attach 同层；引擎已持有 ticket 与 Outbox 端口 | 改动落在核心，需单测覆盖 |
| B | `Runtime.receive` + 独立 `try/catch` + 日志（上次做到这一步）| 改动小 | 上次未验证成功，写入路径存疑 |
| C | `sources/github.ts` 轮询时直接发 | 时机最早 | 源层没有工单/频道上下文，需额外查询，不可行 |
| D | 提示词驱动协调者回帖 | 零代码 | 已验证不可行 |

## 10. 实施步骤（建议）

1. 先补日志可见性：确认插件 `console.error` 能落到容器日志（上次 `.artifacts` 只有 3 行）；
2. 在 `Engine.attach` 内实现通知（方案 A），带 FR-3 的去重与节流；
3. 单测：基线不通知、sha 变化通知一次、节流不丢事件、关闭 PR 不通知；
4. 端到端：真实 PR 推一次提交 → 核对话题消息 + outbox `sent`；
5. 文档：把实现结论回写到《GitHub项目工人设计》与本文件状态行。

## 11. 范围外

- 评论（不带计划号）是否需要同步到飞书 —— 另议；
- 把返工通知合并进协调者的一条汇总消息 —— 另议；
- GitHub 侧的回执（在 PR 里留言）—— 不做。
