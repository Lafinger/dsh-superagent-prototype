# 需求：同一 PR 推送返工后飞书回帖

> 版本 v1.1 ｜ 状态：未实现（待办） ｜ 更新：2026-11-27 ｜ 优先级：中

## 1. 背景与目标

首次提交结果 PR 已经能自动衔接（PR 正文写 `归属计划 #N` → 挂到计划工单 → 协调者在飞书回帖）。但**同一 PR 的后续推送（返工）** 不会产生任何飞书消息，需求方看不到"已收到返工版本"，也不知道该以哪个提交为准。

**目标**：同一 PR 每推送一次新提交，工单原始的飞书话题里就出现一条中文通知，说明这是返工版本及对应提交。

## 2. 范围

**做**

- 只处理"同一 PR 的 head 提交变化"（追加 commit、force push）；
- 每次推送都通知，**不合并、不限次数**；
- 通知语言固定中文；
- 通知由 **host 代码直接发出**，不依赖模型判断。

**不做**

- 评论（无论是否带计划号）**不同步**到飞书；
- 不在 GitHub 侧回执（不在 PR 里留言）；
- 通知里不附改动文件数/增删行数；
- 不合并多条推送为汇总消息。

## 3. 需求

### R1 检测推送

- 每轮轮询 `GET /repos/{owner}/{repo}/pulls?state=all&sort=updated&direction=desc`，读取每个 PR 的 `head.sha`；
- 与基线 `github-pull-head:<PR号>` 比较，**sha 变化即一次推送**；
- 首次见到某 PR 只建立基线，不通知；
- PR 已 `closed`/`merged` 后只更新基线，不通知。

### R2 通知

- 目标：工单的飞书话题（`ticket.channels` 中 `source = feishu` 的 `chatId` + `messageId`）；
- 文案固定中文，包含 PR 号、短 sha（7 位）、新提交标题：

  ```
  PR #9 有新提交（583ba58「文档：追加重置设计 v1.5 复核」），返工版本已记录。
  ```

- 通知**不含 @**；是否另行 @ 人由协调者自行判断（协调者若再发一条带 @ 的消息，允许并存）。

### R3 去重

- 同一 `(工单, sha)` 只通知一次（消息 ID 含 sha）；
- **不做时间节流**：不同 sha 每次都通知，只要有推送就回复；
- 通知失败不影响 attach，也不影响协调者流程。

### R4 可观测

- 失败不得静默：应用日志写 `[push-notice] …`，含 PR 号、sha、原因；
- 成功后可查到 outbox 回执状态为 `sent`。

## 4. 验收标准

1. 同一 PR 追加一个 commit → 工单飞书话题出现通知，sha 与提交标题正确；
2. 同一 PR 做 force push → 同样出现通知（新 sha）；
3. 同一 sha 重复轮询 → 不产生第二条；
4. 连续多次推送（间隔任意短）→ **每次都出现通知**（一条不少、不合并）；
5. 新 PR 首次被轮询到 → 不通知（仅建立基线）；
6. 已合并/关闭的 PR 再推送 → 不通知；
7. 通知失败时日志有 `[push-notice]` 记录，且 attach 与协调者流程不受影响；
8. 回归：现有"成果直通"（新 PR 挂单 + 协调者回帖）行为不变。

## 5. 实现建议

| 项 | 建议 |
|---|---|
| 落点 | `core/engine.ts` 的 `attach()`：检测 `trigger.meta.kind === 'push'` 后直接 `outbox.send(...)`（与已证明可用的 attach 同层，引擎已持有 ticket 与 Outbox 端口）|
| 触发来源 | `sources/github.ts` 增加 PR head 轮询，产出 `github-push:<PR号>:<sha>` 触发器（ID 含 sha，天然每次唯一）|
| 步骤 | ① 先确认插件日志能落到容器日志 → ② 实现通知 → ③ 单测（基线/变化/同 sha/关闭 PR）→ ④ 端到端验证 → ⑤ 回写本文状态 |

## 6. 已知风险（上一次尝试的教训）

同一目标曾实现四次均失败并回退（commit `8ed5800`）：

| 尝试 | 做法 | 结果 |
|---|---|---|
| 1 | 在 `attach` 的 note 里要求回帖 | note 在输入已投递后被丢弃，模型看不到 |
| 2 | 命令写入触发器正文 + 提示词例外 | 被 `dispatch.md`「不重复里程碑」压制，仍不发言 |
| 3 | 直接改最强抑制点并重置会话 | 模型改为"继续等待，不催促"，仍不发言 |
| 4 | host 在 `Runtime.receive` 内 `outbox.send` | attach 正常但通知未落库，当时容器半死、日志不可见 |

**结论**：不要用提示词驱动"是否发言"；通知必须 host 发；落点换到 `Engine.attach`，并先解决日志可见性。
