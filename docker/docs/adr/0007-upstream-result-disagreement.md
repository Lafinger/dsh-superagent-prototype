# 上游成果完成后下游有异议：前置验收 + 返工两轮 + 升级

## Context
计划确认阶段的异议已由 ADR 0006 处理。但如果**上游已提交成果、下游（下一个角色）对上游成果有异议**，此前提示词没有定义：「成果贴链接 → @ 下游开始 → 最后一个成果 → 宣告完成」，且"从不判断成果好坏、从不合并"。异议时行为不确定，可能把上游当已完成继续推进。

## Decision
引入**成果交接验收**：
1. 上游提交成果 PR 后，协调者 @ 下游先验收；下游「接受」→ 审批人合并 → 下游开工。
2. 下游「异议 + 理由」→ 协调者**不合并、不推进**，转上游返工；上游改后重新提交，回到验收；**每对上下游最多 2 轮返工**。
3. 2 轮仍不一致，或异议涉及需求/验收标准 → 升级裁决。
4. 若上游**已合并**：不回滚历史，由上游开**修复 PR**，合并后下游再验收。
5. 协调者始终不判断成果好坏、不合并；**未解决不得进入下一环、不得宣告完成**。

## 审批人冲突（escalation）
- 当「审批人」恰好是「被异议的角色」本人（如 demo 中产品=审批人），自己判自己有利益冲突。
- 决策：`settings/team.yml` 增加**可选 `escalation`**（默认=原始提需求者）；审批人冲突或无裁决时升级给 escalation。
- 真实团队应把 `escalation` 设为中立第三方。

## Considered Options
- 直接合并后再返工：返工代价大、历史脏。
- 无限返工：不可控。
- **前置验收 + 2 轮返工 + 升级 escalation**（采用）。

## Consequences
- 异议有确定路径与止点；不能误推进、不能误宣告完成。
- 合并权始终在审批人；协调者只路由。
- 依赖 `escalation` 配置；留空则回退到原始提需求者。
- 已合并的上游成果用"修复 PR"返工，不改写历史。
