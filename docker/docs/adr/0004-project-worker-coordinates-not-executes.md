# Project Worker 是协调者：归档资料、出计划、跟踪成果，不执行也不验收

在 [ADR 0003](0003-github-as-project-library-and-project-worker.md) 里，单一 Project Worker 被定义为“依据仓库推进项目、提交成果 PR”的**执行者**。深入测试发现真实项目里“产品 / 前端”是两位真人：他们各自完成并提交成果。若 worker 自己也动手产出成果，会与人的职责混淆，也无法体现多人协作与人工审批。

现在决定：Project Worker 的角色改为**协调者**。

- **归档**：读取客户需求等资料，依文件名与内容自动归入 GitHub 资料库的对应目录，不要求人指定路径。
- **计划**：在飞书话题线程内先给**计划草案**，逐角色（先产品、后前端）写明：任务、交付物、成果目录、提交方式（飞书或 PR）、评审与合并人、依赖顺序（前端基于产品**已合并**的成果）。产品与前端均表示同意后，才落为正式 `plan` issue 并回贴链接。
- **跟踪**：产品与前端各自完成并**自检**成果，通过飞书或 GitHub 提交；有人在飞书贴出成果 PR 链接后，worker 通知下一角色；前端成果到达即宣告计划完成。
- **边界**：worker **不写产品 / 前端成果、不评审、不验收、不合并、不关闭 issue**。成果的责任在提交者。

## Considered Options
- **worker 兼执行者**（ADR 0003 的行文，放弃）：与“产品 / 前端是真人、成果各自提交”的协作模型冲突；单人演示可行，多人项目职责错位。
- **两个角色 agent（产品 agent / 前端 agent）**（放弃）：违背“单一 Project Worker”的决定，工程量大。
- **协调者 + 人工驱动**（采用）：仍是单一 worker，提示词 / skill 层面即可承载。

## Consequences
- worker 提示词与 `dsh-superagent-project` skill 改写为协调者流程；计划必须写明每角色的任务 / 交付物 / 目录 / 提交与审批 / 依赖 / 自检责任。
- 现有框架**不会自动**把真人自开的 PR 绑定到计划，也读不了飞书里的非图片文件附件。因此约定：需求文档由人先上传到仓库、再令 worker 归档；成果 PR 链接由人在飞书贴出。这两点是已知缺口，如需全自动要改插件代码（暂不做）。
- “成果负责方”由 worker 转给提交者（产品 / 前端）；worker 的“完成”＝跟踪到前端成果提交并通知。
