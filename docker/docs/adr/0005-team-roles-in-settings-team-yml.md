# 团队岗位由项目内 settings/team.yml 定义（配置驱动，而非提示词写死）

此前协调者把岗位写死在提示词 / skill 里（固定“产品，然后前端”），也不绑定具体飞书账号：换一个需要“设计 / 测试 / 后端”的项目，它仍只会产出产品 + 前端；@ 谁、谁审批，只是运行时读群成员临时决定。

现在决定：**项目有哪些岗位、各由谁担任、谁评审合并，统一写在项目仓库的 `settings/team.yml`**，协调者读它来分配任务、@ 人、指定审批合并人。提示词与 skill 只引用“team file 里的角色”，不再写死任何岗位名或人名。缺少某个岗位或人员时，协调者让人补齐 `settings/team.yml` 并等待，不擅自猜测。

## Considered Options
- **提示词里写死岗位**（原状，放弃）：不可按项目适配，也无账号绑定。
- **部署级设置里维护团队**（放弃）：跨项目共用一份，切项目要改全局配置，边界不清。
- **纯动态解析需求自动推断岗位**（放弃）：不可控，且飞书 open_id 仍无来源。
- **项目内 settings/team.yml（配置驱动）**（采用）：跟着项目走、可评审、可版本化。

## Consequences
- 每个项目仓库新增 `settings/team.yml`；换岗位/换人只改这个文件，不改代码与提示词。
- 协调者必须先读 `settings/team.yml`；缺失或字段不全时，需人补齐后再生效（属于人工配置决策）。
- 岗位仍是“人维护的清单”，不是自动生成的；需求若引入新岗位，要同步补进 `settings/team.yml`。
- 飞书身份用 open_id 绑定，避免同名歧义；没有 GitHub 账号的人可留空 GitHub 登录，由飞书提交成果。
