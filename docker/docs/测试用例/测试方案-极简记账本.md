# 测试方案：协作全流程（极简记账本）

> 目的：验证 DSH 项目协调者在真实双角色协作下的主链路与异常分支。
> 案例与需求原文见 [极简记账本-协作案例.md](./极简记账本-协作案例.md)。
> 环境：镜像 `6cec0e1`、容器 `dsh-superagent-project-dsh-superagent-1`(3083)、bot「项目助手」、群「superagent测试」。

## 一、环境与前置
- 部署基线（开测前先跑 TC0）。
- `settings/team.yml`：产品=Lafinger、前端=陈小二、审批人=Lafinger、escalation=Lafinger。
- 两个账号都要能发言：**Lafinger（产品/审批/升级）** 与 **陈小二（前端）**。
- ⚠️ 当前 `approver`、`escalation`、`product` 都是 Lafinger → 涉及"产品成果被异议"时无法真正中立裁决；涉及审批冲突的用例只验证**机制触发**，不验证"第三方裁决"。
- 需求一律**发文字**（飞书源不解析 PDF/Word 附件）。

### TC0 基线冒烟（开测前）
- **步骤**：我执行核验（见第六节命令）。
- **预期**：`setup.problem` 空；github/feishu/runtime/delivery=`ready`；`login=lafinger-agent`；0 工单；`settings/team.yml` 含 escalation。

---

### TC1 主链路（P0，必须通过）
> 本轮用**新案例名「极简记账本 V2」**，避免与仓库历史 #10–#14 去重而不新建计划。

**TC1 发送内容（复制到群「superagent测试」，@项目助手 后粘贴）**
```
【需求：极简记账本 V2（单页应用）】
（这是 V2 的独立新需求，请重新归档并新建计划，不要复用历史「极简记账本」计划。）

背景
我想做一个自己用的极简记账网页，手机上也能用，用来快速记录每天的支出，并查看本月花了多少、各个分类各占多少。

目标用户
个人用户（主要是我自己），主要在手机浏览器使用，偶尔电脑。

核心功能
1. 记一笔支出：填写金额（元，必填，>0）、分类（餐饮/交通/购物/娱乐/其他，必选）、备注（可选，最多50字）、日期（默认今天，可改）。
2. 支出列表：按日期倒序显示；每条可删除（删除前需确认）。
3. 统计：显示本月总支出；按分类汇总金额和占比（百分比，保留整数即可）。
4. 数据保存：刷新/关闭浏览器后数据不丢（用浏览器本地存储）。
5. 空状态：没有任何记录时给出友好提示和使用引导。

非功能要求
- 单页即可（index.html），不需要登录、不需要后端、不需要联网同步。
- 手机宽度（375px）下布局正常，不能有横向滚动；桌面（1280px）也好看。
- 操作简单直观，点两下就能记一笔。

交付内容
- 产品：一份产品方案（页面结构、字段与校验规则、交互流程、统计口径、空状态、验收清单）。
- 前端：基于产品方案实现网页，交付 index.html、桌面和手机截图各一张、一页简短使用说明。

验收标准
- 能成功新增、删除记录；金额非法时给提示。
- 本月总计与分类占比计算正确。
- 刷新后数据仍在。
- 手机 375 宽和桌面 1280 宽显示正常、无横向滚动。
- 空数据时有空状态提示。
```

按顺序执行，**每步完成把现象/截图发我，我核验后再下一步**。

1. **发需求**：群里 @项目助手 粘贴上面的 V2 需求原文，发送。
   - 预期：机器人回执；`materials/requirements/` 新增需求 md（有一次提交）；在线程贴计划草案并 @产品 @前端。
   - 核验：仓库 contents/commits；`/tickets`；`/threads`。
2. **双方确认**：Lafinger 回「同意」；陈小二回「同意」。
   - 预期：集齐后创建正式 **Plan issue + 产品 Task + 前端 Task**（plan/task 标签），贴链接。
   - 核验：GitHub issues 数量/标签/正文是否含 角色顺序、交付目录、提交方式、审批人。
3. **产品交付**：Lafinger 写 `results/product/产品方案-记账本.md`，开 PR，**PR 链接贴线程 @机器人**。
   - 预期：机器人 @陈小二 请其验收。
   - 核验：PR 存在、文件内容、机器人消息。
4. **下游验收**：陈小二回「接受」。
   - 预期：审批人合并；机器人通知陈小二开工。
   - 核验：PR 状态 merged；机器人消息。
5. **前端交付**：陈小二做 `results/frontend/index.html`+2 截图+`说明.md`，开 PR，链接贴线程。
   - 预期：机器人 @Lafinger 验收/进入完成。
6. **验收+完成**：Lafinger 回「接受」→ 合并。
   - 预期：机器人宣告完成；**close Plan issue 与两个 Task issue**（不 close 其它）；plan issue 有完成评论。
   - 核验：issue 状态 closed、其它 issue 不受影响、`/tickets` 该工单结束。
- **通过标准**：6 步全部符合预期；无越权（未自行写成果/未合并/未错误 close）。

---

### TC2 计划异议：改稿一轮（P1）
- 前置：TC1 到"计划草案"步骤（新开一个需求，或复用但先停掉旧工单）。
- **步骤**：陈小二回「不同意：请先明确手机端是否离线可用、是否支持数据导出」。
- **预期**：不建正式计划；机器人**改稿回应**并重新 @ 双方求同意（第 1 轮）；随后双方回「同意」→ 正常出正式计划。
- **核验**：确认正式计划出现前没有任何 plan issue；线程里有改稿版本；改稿内容回应了那两点。

### TC3 计划异议：2 轮后升级（P1）
- **步骤**：陈小二连续两轮回「不同意 + 理由」。
- **预期**：第 2 轮后机器人 **@审批人（Lafinger）** 陈双方立场；Lafinger 回「继续」→ 出正式计划；或回「停止」→ 工单结束/blocked；不回 → blocked。
- **核验**：机器人确实 @ 了审批人；未擅自出计划；按审批人答复动作。

---

### TC4 成果异议：返工循环（P1）
- 前置：TC1 到"产品交付、等待陈小二验收"。
- **步骤**：陈小二回「异议：产品方案缺少分类占比口径，需要补充」。
- **预期**：不合并、不推进；机器人把异议转给 Lafinger（产品）返工；Lafinger 改 PR 后重新提交；陈小二再验收。**最多 2 轮**。
- **核验**：PR 在异议期间未被合并；机器人消息指向产品返工；返工后重新走验收。

### TC5 成果异议：2 轮后升级（P1）
- **步骤**：陈小二连续两轮异议。
- **预期**：第 2 轮后 @审批人裁决；审批人「继续」→ 推进；「停止」→ 工单 dropped/blocked。
- **核验**：同 TC3，只是发生在成果阶段。

---

### TC6 飞书提交成果（P2，H2）
- **步骤**：产品阶段，Lafinger **不发 PR**，直接把方案要点/链接**发在飞书线程**作为成果。
- **预期**：机器人按"飞书提交"处理；陈小二验收通过即视为交付，**不要求合并**，直接进入前端阶段。
- **核验**：机器人未尝试合并、未卡在"等合并"。

### TC7 team.yml 异常（P2，H3）
- **步骤**：临时把 `settings/team.yml` 改坏（删掉 `approver:` 或写成非法 YAML），发需求/进行到一半。
- **预期**：机器人**不猜**，说明哪里不对、请修复；无法继续 → **blocked**。
- **核验**：无正式计划产出；工单 blocked；恢复 team.yml 后可继续。
- **清理**：务必恢复 team.yml（用 git 或我帮你重置）。

### TC8 完成时 close（P2，H6）
- **步骤**：TC1 走到最后一步验收通过。
- **预期**：机器人 close **Plan + 两个 Task** issue，并留完成评论；**不 close** 其它 issue（如测试 issue #9 之类）。
- **核验**：逐条查 issue state；其它 issue 状态不变。

### TC9 需求含糊（P2，H7）
- **步骤**：发一条含糊需求（例："帮我做个页面，随便弄好看点"）。
- **预期**：机器人**不进入确认**；在计划里列 open questions，并 @客户澄清（缺验收标准）。
- **核验**：无正式计划；线程有澄清问题。

### TC10 中途新需求（P2，H8）
- **步骤**：TC1 计划已确认后，同线程再发一条**不同**的新需求。
- **预期**：作为**新请求单独计划/确认**，不混入当前计划。
- **核验**：原计划不变；出现新的计划/工单。

### TC11 非角色发言（P2，H9）
- **步骤**：让一个**非 team.yml 角色**的账号（如旧「测试助手」或第三人）在群里回「同意/开始」。
- **预期**：机器人**忽略**并说明"只认 team.yml 中的角色/审批人/升级人"；不据此推进。
- **核验**：计划未被该发言触发。

### TC12 人员变动（P3，H10）
- **步骤**：临时把前端 `feishu_open_id` 改错/移除，走到确认环节。
- **预期**：机器人以**当前 team.yml** 为准，@失败/缺人 → **blocked** 等补；恢复后继续。
- **核验**：blocked 且提示补人；恢复后正常。

### TC13 进度提问（P3，M5）
- **步骤**：进行中，人类问「现在进度如何？」。
- **预期**：机器人基于 ticket/issue 回答；**不改状态、不执行外部动作**；不把提问当同意。
- **核验**：状态不变。

## 九、风险与注意
- **中立性**：approver/escalation 目前都= Lafinger，涉"产品成果被异议"时是自判，只验机制不验裁决。
- **陈小二依赖**：双人确认/验收需陈小二账号在线；否则流程会停（正好可当 H10/超时场景观察）。
- **附件**：需求用文字；PDF/Word 不被解析。
- **一次一需求**：避免重复工单；用例间先收尾（停止/完成旧工单）再开新用例。
- **未实现项**（H1 超时不回复、H4 审批人不合并、H5 下游不开工、M1/M2/M3/M4/M6/M7/M8）本轮**只观察**，如出现卡住属已知识别缺口。

## 十、本轮范围外（仅观察）
超时类（H1/H4/H5）：不发催办、不自动 blocked，可能表现为"一直等"——观察到就记录，不作为失败。其余 M 系列同理。
