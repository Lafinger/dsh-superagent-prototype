## 二、需求文档（客户直接复制，@项目助手 发送；务必用文字，不要附件）
```
【需求：极简记账本（单页应用）】

背景
我想做一个自己用的极简记账网页，手机上也能用，用来快速记录每天的支出，并查看本月花了多少、各个分类各占多少。

目标用户
个人用户（主要是我自己），主要在手机浏览器使用，偶尔电脑。

核心功能
1. 记一笔支出：填写金额（元，必填，>0）、分类（餐饮/交通/购物/娱乐/其他，必选）、备注（可选，最多50字）、日期（默认今天，可改）。
2. 支出列表：按日期倒序显示；每条可删除（删除前需确认）。
3. 统计：显示本月总支出；按分类汇总金额和占比（百分比，保留整数即可）。
4. 数据保存：刷新/关闭浏览器后数据不丢（用浏览器本地存储）。
5. 空状态：没有任何记录时给出友好提示和使用引导。

非功能要求
- 单页即可（index.html），不需要登录、不需要后端、不需要联网同步。
- 手机宽度（375px）下布局正常，不能有横向滚动；桌面（1280px）也好看。
- 操作简单直观，点两下就能记一笔。

交付内容
- 产品：一份产品方案（页面结构、字段与校验规则、交互流程、统计口径、空状态、验收清单）。
- 前端：基于产品方案实现网页，交付 index.html、桌面和手机截图各一张、一页简短使用说明。

验收标准
- 能成功新增、删除记录；金额非法时给提示。
- 本月总计与分类占比计算正确。
- 刷新后数据仍在。
- 手机 375 宽和桌面 1280 宽显示正常、无横向滚动。
- 空数据时有空状态提示。
```

## 三、逐步操作（你做什么 / 预期机器人 / 我帮你核验）
### 阶段 0：准备
- 确认部署健康（已核验：见文末基线）。
- 确认 `settings/team.yml` 在仓库（已存在，产品=你、前端=陈小二、审批=你）。

### 阶段 1：发需求
- **你做**：在群「superagent测试」里 **@项目助手**，粘贴上面的需求原文，发送。
- **预期**：机器人回执；把文档归档到 `materials/requirements/`（产生一次提交）；随后在线程贴「计划草案」并分别 @产品 @前端。
- **我核验**：仓库是否新增 requirements 文件与提交；是否新建工单 ticket；飞书线程是否出现。

### 阶段 2：双方确认
- **你做**：产品（你，Lafinger）在线程回「**同意**」；前端（陈小二）在线程回「**同意**」。
- **预期**：集齐两票后，机器人创建正式 Plan issue + 产品/前端两个 Task issue（带 plan/task 标签），并把链接贴回线程。
- **我核验**：ticket/thread 状态；GitHub 上是否出现 plan/task issue；issue 正文是否写明「角色顺序 / 交付目录 / 提交方式 / 审批人」。

### 阶段 3：产品交付
- **你做**：产品写 `results/product/产品方案-记账本.md`（内容要点见第四节），用你自己的 GitHub 账号（Lafinger）开 PR；**把 PR 链接贴到飞书线程并 @机器人**（也可把方案要点直接发飞书）。
- **预期**：机器人记录产品成果，@前端 通知可开始。
- **我核验**：PR 是否存在、作者是否 Lafinger、文件内容；机器人是否 @ 了陈小二。

### 阶段 4：前端交付
- **你做**：前端（陈小二）基于已合并的产品方案实现 `results/frontend/index.html` + 两张截图 + `说明.md`，开 PR；**PR 链接贴飞书线程 @机器人**。
- **预期**：机器人宣布「计划已完成」。
- **我核验**：PR、文件、截图；ticket 是否结束；是否还有遗留。

### 阶段 5：审批合并
- **你做**：审批人（Lafinger）评审并合并两个 PR（GitHub 或飞书）。
- **我核验**：PR 状态 merged、无遗留工单。

## 四、交付要点（降低返工）
- **产品方案应包含**：页面结构（录入区 / 列表区 / 统计区 / 空状态）、字段与校验规则、交互与状态（新增、删除确认、日期默认、分类选择）、统计口径（本月=按记录日期所在月；分类占比=分类金额/本月总额，保留整数）、响应式断点、给前端的实现约束（纯静态、index.html、localStorage）、验收清单。
- **前端实现应满足**：单文件 `index.html`（原生 JS 即可）、金额建议以「分」为整数存储避免浮点误差、删除需二次确认、localStorage 一个 key、375 宽无横向滚动、1080/1280 桌面正常；附桌面与手机截图、一页说明。
- 结果 PR 链接务必**贴飞书线程并 @机器人**；机器人不合并，合并由审批人做。

## 五、注意事项
- 需求**用文字**发，不要 PDF/Word 附件（飞书源不解析附件）。
- 两个角色都要回「同意」，否则会卡在确认阶段。**若陈小二账号暂时不可用**，流程无法完成双人确认——告诉我，我们商量临时替代（例如临时把 `settings/team.yml` 的 frontend 换成你能控制的另一个账号，并同步改动）。
- 同一案例只发一次需求，避免重复工单。
- 人类 PR 不会被自动当作"机器人成果"，所以**链接要贴飞书**让协调者接续。

## 六、异议流程（计划异议 ADR 0006 / 成果异议 ADR 0007）
**计划阶段异议**
- 任一方回「不同意 + 理由」→ 不建正式计划；协调者改稿回应、重新 @ 双方求同意，最多 2 轮。
- 2 轮仍不同意 → @ 审批人（`approver`）裁决；若审批人=被异议角色或无裁决 → 升级 `escalation`（默认原始提需求者）。
- 说「调整/继续」照办；「停止」→ dropped；无裁决 → blocked。

**成果阶段异议（上游已完成/已提交，下游对上游成果有异议）**
- 上游成果先由下游验收：下游「接受」→ 审批人合并 → 下游开工。
- 下游「异议 + 理由」→ 不合并、不推进，转上游返工重交；每对上下游最多 2 轮。
- 2 轮仍不一致 → @ 审批人裁决；冲突或无裁决 → 升级 `escalation`；「停止」→ dropped，无裁决 → blocked。
- 上游已合并 → 由上游开修复 PR，合并后下游再验收。
- 全程不判断成果好坏、不合并、未解决不推进、不宣告完成。
