# 设计方案：项目工时统计 v3.0（四项时刻 + 流程调整）


> 版本 v1.0 ｜ 状态：已实现（v3.1） ｜ 更新：2026-11-27
> 需求口径：**工时 = 交付时长**；**只保留四个基础时刻**；**不做面板**；
> 同时调整智能体的推进流程：PR 一律等到计划关闭前才合并，上游提交即放行下游。

---

## 1. 变更摘要（相对 v2.1）

| 项 | v2.1 | v3.0 |
|---|---|---|
| 指标数量 | 5 个时刻 + 5 个差值（B1–B10）| **4 个时刻**（B1–B4）+ 3 段差值 |
| 合并时机 | 下游验收后由审批人合并 | **计划关闭前统一合并**，此前不允许合并 |
| 下游启动 | 上游合并后才开始 | **上游提交 PR 即通知下游开始** |
| 异议路径 | 退回上游 → 最多两轮 → 升级 | 下游**直接找上游或智能体**说明，上游返工 |
| 收尾 | 最后一个角色验收后合并 | **智能体先合并全部 PR，再通知并关闭计划** |
| 接口 | 三种格式（md / csv / json）| **仅 JSON**；新增 `plan/task/pull` 的 `_url` 与 `_content` 字段 |

---

## 2. 四个基础时刻

| 编号 | 名称 | 定义 | 数据来源 |
|---|---|---|---|
| **B1** | 话题开始时刻 | 需求提出者在该话题发出的**第一条消息**时间（话题起点）| `kv plan-link:<N>`（worker 通过 `orchestrator_report(plan_number)` 登记 → 该工单 `origin` 消息时间）；无登记时回退到消息里的 `/issues/<N>` 链接，都没有则留空 |
| **B2** | 正式发布时刻 | 计划/任务正式创建的时刻 | GitHub 计划 issue（或任务 issue）`created_at` |
| **B3** | 首次提交时刻 | 该任务**第一个**结果 PR 的创建时刻 | GitHub 该任务关联 PR 的最早 `created_at`；飞书交付时取提交消息时间 |
| **B4** | 计划完成时刻 | 计划 issue 关闭的时刻 | GitHub 计划 issue `closed_at`（缺失时用工单 `ended.at`）|

### 派生（只做相邻相减，不做汇总/趋势/瓶颈）
| 指标 | 公式 | 含义 |
|---|---|---|
| 规划期 | B2 − B1 | 话题开始到正式发布，反映"需求落地"速度 |
| 响应期 | B3 − B2 | 发布到首次提交，反映"开工"速度 |
| 收尾期 | B4 − B3 | 首次提交到计划完成，反映"验收与合并"速度 |
| 全周期 | B4 − B1 | 端到端 |

## 4. 配套流程调整（本次的重点）

### 4.1 新旧规则对照

| 环节 | 现有规则（SKILL 第 20、22 行）| 新规则 |
|---|---|---|
| 上游提交后 | 下游先验收，通过后由审批人合并，下游才开工 | **提交即通知下游开工**，不等待合并 |
| 异议 | 退回上游修订，最多两轮，再升级审批人/升级人 | 下游**直接向智能体或上游说明原因**，上游返工即可；智能体记录轮次 |
| 合并 | 验收通过即合并 | **计划关闭前一律不合并**，全部 PR 挂起 |
| 收尾 | 最后一个角色验收后合并、关闭 | **智能体先合并全部 PR**，发通知，再关闭计划与任务 |

### 4.2 与现有约束的冲突（必须先解决）

1. **安全句冲突**：`prompts/worker.md` 第 6 行现为"绝不直接合并 PR 或开启自动合并"，新流程要求智能体在收尾时合并——**这句必须改写**，`tests/cards.spec.ts` 的逐字断言同步更新。
2. **审批人角色变化**：现在"审批人审阅并合并"；新流程里合并由智能体执行，审批人退化为"确认计划完成"。是否保留审批人的人工合并权，需要你定（见 Q5）。
3. **合并前置条件**：保留"CI 必须绿"；合并失败（冲突、CI 红）→ 计划转 `blocked` 并回帖，不硬关。
4. **并行带来的返工**：下游在上游未定稿时开工，产物可能返工；这是新流程的固有代价，需要在计划里写明"以上游最新提交为准"。

## 5. 数据获取细节

| 时刻 | 取值方式 | 缺失处理 |
|---|---|---|
| B1 | 优先 `kv plan-link:<N>`（工单原始需求消息时间）；其次消息里出现 `/issues/<N>` 链接的那条 | 都没有 → 标 `b1` 缺失，不做推断 |
| B2 | 计划 issue `created_at` | 必须有，否则整行无效 |
| B3 | 该任务关联 PR 的最早 `created_at`；飞书交付取提交消息 | 缺失 → 标「未提交」|
| B4 | 计划 issue `closed_at`；缺失取工单 `ended.at` | 缺失 → 标「进行中」|

关联规则沿用：PR 正文显式引用任务号优先，否则按任务关闭时间就近匹配。

## 6. 接口与响应（仅 JSON）

| 请求 | 返回 |
|---|---|
| `GET /orchestrator/api/timesheet?plan=N` | `plans` 里只有一个元素 |
| `GET /orchestrator/api/timesheet` | `plans` 包含全部计划 |

统一返回分层结构（v2）：

```json
{
  "schema_version": 2,
  "project": { "id": "…", "name": "…" },
  "plans": [
    {
      "number": 6,
      "url": "…",
      "title": "…",
      "content": "…",
      "roles": [
        {
          "key": "design",
          "name": "设计岗（产品）",
          "person": "陈小二",
          "tasks": [
            {
              "number": 7,
              "url": "…",
              "title": "…",
              "content": "…",
              "pull": { "number": 4, "url": "…", "title": "…", "content": "…" },
              "timestamps": {
                "requirement_start": "…",
                "plan_published": "…",
                "submitted": "…",
                "plan_completed": "…"
              },
              "durations": { "planning": 0.35, "response": 0.45, "closing": 15.7, "total": 16.5 },
              "missing": []
            }
          ]
        },
        {
          "key": "approver",
          "name": "管理岗",
          "person": "陈锦鸿",
          "tasks": [],
          "coordination": {
            "timestamps": { "requirement_start": "…", "plan_published": "…", "plan_completed": "…" },
            "durations": { "confirm": 0.35, "close": 16.15 }
          }
        }
      ]
    }
  ]
}
```

### 6.1 字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `schema_version` | number | 固定 `2` |
| `project.id` / `project.name` | string | 仓库全名与项目名 |
| `plans[].number` / `url` / `title` / `content` | number / string | 计划 issue；正文**只出现一次** |
| `plans[].roles[].key` / `name` / `person` | string | 岗位标识、岗位名、负责人 |
| `roles[].tasks[]` | array | 该角色的任务；管理岗为空数组 |
| `tasks[].number` / `url` / `title` / `content` | number / string | 任务 issue |
| `tasks[].pull` | object? | 结果 PR（`number`/`url`/`title`/`content`）；**任务没有 PR 时整个字段缺失** |
| `tasks[].timestamps` | object | `requirement_start`（原 B1）/ `plan_published`（B2）/ `submitted`（B3）/ `plan_completed`（B4）；缺失的时刻不出现 |
| `tasks[].durations` | object | `planning` / `response` / `closing` / `total`（小时）；无法计算时不出现 |
| `tasks[].missing` | string[] | 缺失时刻的语义名 |
| `roles[].coordination` | object? | **仅管理岗**：`timestamps` 三项 + `durations.confirm` / `close`；**不含 events** |

### 6.2 规则

- 计划、任务、PR 的正文各出现一次，不再随行重复（当前实测可省约 26% 体积）；
- 时间与时长使用语义名，不再使用 `b1`–`b4`；
- 团队文件没有 `approver` 时，`roles` 里不出现 `approver` 节点；
- 没有计划时返回 `plans: []`。

## 8. 边界与不做

- **不做**：汇总/平均/中位、趋势、瓶颈判定、工作日折算、返工轮次统计、面板；接口**只保留 JSON**（不再提供 CSV 与 Markdown 两种请求方式）。
- 计划进行中：B4 空，行标「进行中」，照常出表。
- 多人多任务：一行一个任务，B1/B4 在计划内相同。

## 9. 管理岗（roles 里的 `approver` 角色）

管理岗出现在 `plans[].roles[]` 里，`key = "approver"`、`tasks: []`，只带 `coordination`。它不提交 PR、不合并 PR，也不记录审阅事件——**`events` 已移除**，接口只给三个时刻与两段时长。

| 字段 | 值 | 来源 |
|---|---|---|
| `timestamps.requirement_start` | 需求开始 | 同任务行的 `requirement_start`（`kv plan-link` / 消息链接）|
| `timestamps.plan_published` | 计划发布 | 计划 issue `created_at` |
| `timestamps.plan_completed` | 计划完成 | 计划 issue `closed_at` |
| `durations.confirm` | 发布 − 开始 | 计算 |
| `durations.close` | 完成 − 发布 | 计算 |

规则：

- 三个时刻**复用任务行的同名时刻**，不另起编号；
- 审批人取自 `settings/team.yml` 的 `approver` 块（`name` / `feishu_name`）；缺该块时不生成这个角色节点；
- 管理岗的审核是**异步**的：上游提交即放行下游，可随时要求返工，下游按新结果重整；异议轮次不设上限；
- 团队文件不再有 `escalation`，争议由管理岗裁决，必要时先与客户确认；
- 审阅事件的审计留在飞书消息与工单里，**不进本接口**。
