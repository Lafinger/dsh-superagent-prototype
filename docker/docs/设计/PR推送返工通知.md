# 设计：同一 PR 推送返工后的飞书通知

> 版本 v2.0 ｜ 状态：已实现 ｜ 更新：2026-11-27

## 1. 目标

同一 PR 每推送一次新提交（追加 commit / force push），都要在工单的飞书话题里留下通知，说明"这是返工版本 + 是哪个提交"，让需求方与下一岗位知道该以哪个提交为准。

## 2. 实现方式

| 组成 | 位置 | 说明 |
|---|---|---|
| 推送检测 | `src/sources/github.ts` → `pollPullHeads` | 每轮拉 `pulls?state=all&sort=updated&direction=desc&per_page=30`，比较每个 PR 的 `head.sha` 与基线 `github-pull-head:<PR号>`；变化即推送 |
| 触发器 | `src/sources/github-trigger.ts` → `pullPushTrigger` | ID 为 `key('github-push', PR号, sha)`（同 sha 只产生一次）；正文 = PR 标题 + 正文 + `PR #N 推送了新提交 <sha7>「<提交标题>」（返工版本，head 提交已改变）。`；meta 带 `kind: 'push'` 与 `sha` |
| 投递 | `src/app/runtime.ts` → `receive` | 触发器正文含 `归属计划 #N` 时挂到计划工单（attach），从而唤醒协调者 |
| 通知内容 | 协调者（提示词驱动）| 由协调者在话题里回帖，写明 PR 号、短 sha、提交标题，并可 @ 需要重看的人 |

检测细节：

- 首次见到某 PR 只写基线，不通知；
- PR 已 `closed` / `merged` 时只更新基线；
- 同一 PR 60 秒内重复检测只处理一次（`github-pull-notify:<PR号>` 节流）。

## 3. 提示词规则（让协调者"必须说"）

提示词里把"推送"从"重复里程碑"中显式排除，避免它按"无新事项就不发"处理：

| 文件 | 规则要点 |
|---|---|
| `prompts/dispatch.md` | push 不是重复里程碑；收到 `kind=push` 必须在本话题回帖，写明 PR 与新提交；即使无需人工动作、即使只是文档改动、即使此前报过同一 PR，也必须发 |
| `prompts/orchestrator.md` | `Keep progress internal` 之后追加同一例外 |
| `skills/dsh-superagent-project/SKILL.md` | 交接段追加：push 属于新成果，必须报一次 |

## 4. 实际行为（已观察到的现象）

| 场景 | 行为 |
|---|---|
| 单岗推送 | 协调者单独回帖（实测 2026-11-27 17:33「设计 PR #14 已更新」）|
| 多岗连续推送 | **允许合并为一条业务汇报**（实测 18:17「两岗修订已完成」，一条覆盖 `eab01f1`、`d6a481b`）|

**合并是按业务节点组织消息，不是漏报**：每条通知正文必须覆盖本次推送的短 sha。

## 5. 已知限制

| 限制 | 说明 | 结论 |
|---|---|---|
| 允许合并 | 多岗同时返工时，协调者会攒成一条"修订已完成" | **已接受**（业务上更清晰）|
| 通知可能延迟 | 等其它岗位一起汇报时，第一条推送的回帖会晚（实测 18:01 推送 → 18:17 回帖）| 已接受 |
| 轮询窗口内合并 | 轮询周期 60 秒，窗口内多次推送只看得到最终 sha | 已接受 |
| 依赖 GitHub 可达 | 容器到 `api.github.com` 间歇性 TLS 握手超时会导致漏轮询 | 环境问题，需网络稳定 |
| 协调者仍可能沉默 | 提示词不能 100% 保证发言（同一规则曾出现"17:33 回、18:01 不回"）| 接受；如要求"绝对不漏"，改 host 直发 |

## 6. 未采用方案

| 方案 | 未采用原因 |
|---|---|
| host 在 `Engine.attach` 层直发 | 会与协调者的汇总消息重复，且当前提示词路线在正常工作 |
| 评论同步到飞书 | 明确不做 |
| 合并多条为定时汇总 | 明确不做（当前是业务节点合并，非定时）|

## 7. 若将来要求"绝对不漏"

1. 在 `Engine.attach` 内检测 `trigger.meta.kind === 'push'`，由 host 直接 `outbox.send`；
2. 去重：同一 `(工单, sha)` 一次；同一话题 60 秒内已有机器人消息则跳过；
3. 与协调者并存时以 host 消息为"事实回执"，协调者消息为"业务解读"。
