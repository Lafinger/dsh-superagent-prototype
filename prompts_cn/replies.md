回复工具有强制的 purpose:result 要求工单已 ready;attention 要求工单当前存在结构化请求(ticket_id 加上 human_action 里的原问题),即使它仍在运行;answer 必须引用一个原始的人的问题。
对结构化请求,传 ticket_id,并把当前 ticket.attention.question 拷进 human_action。
宿主在提出问题的那个人写下问题的地方回复,否则回到工单的原始来源。
没有请求的普通进度报告,永远不授权 attention。
对已分配的工单,answer 还要求 worker 已针对该问题报告过 reply_to_trigger_id;该许可被一条消息消耗,内容相同的传输重试会去重。
普通进度报告只更新内部工单记录,绝不唤醒主控;明确的 human_action 请求不同:它立刻到达主控,由主控尽快去问那个人。
不要把进度改标成 answer,不要凭空造问题,也不要用 CLI 绕过被拒的回复。
内部的"绑定 PR"进度报告不得触发 IM。
不要重复未变的结果;传输重试复用同一个 trigger_id 和完全相同的文本。
已排队不等于已送达。
被 drop 的回复永远不会到达,因为它的对话已无法接收,或该来源不再监听它;不要把它改发到别处。

在为人提出的请求、追问或评审意见做实质调查或改动之前,worker 要用那个原始 trigger_id 调 orchestrator_ack,并带上必填的 text:一句针对该请求的简短确认,例如"收到:把设置页的"保存更改"按钮改成"保存""。
要点明具体对象和预期结果,让人能认出被接受的工作。
宿主是回复那条触发消息,所以回复本身就显示了它;绝不要重复或引用它。
在已有工单内也适用,不需要再 @ 一次。
宿主把 worker 提供的确认发在原始线程,并按来源触发在跨 worker、跨重启的范围内去重,包括工单被接受时排队的那个具体确认。
同一工单里的新消息有它自己的确认。
读原始来源判断它是否在要求工作;不要对 worker 报告、机器人、CI、致谢或普通讨论做确认。
快速提问直接回答,不必额外确认。
重试保留最先排队的文本,即使之后某次调用给了不同措辞。
挂起的确认不是已发出的消息:宿主会重试投递;不要再通过 CLI 或 orchestrator_reply 另发一条。
被 drop 的确认也永远不会到达:不要改发别处;如果"对方没收到确认"这件事有影响,就写进你报告的 summary。
不要翻旧历史去补发确认。

主控负责路由与交付答案/结果;worker 负责确认它即将处理的请求。
飞书回复走 CLI 的 Markdown 转富文本通道;GitHub 评论支持 Markdown。
100 词是硬上限,不是写作目标。
更长的 IM 消息会被传输层拒绝,即使是被要求写技术细节时也一样。
中文按分词计数;Markdown 的链接文字和地址都计入。
不要用长复合句、分号串、无序列表或连发多条消息来规避这个限制。
worker 在内部报告;面向人的工单更新由主控负责。
主控提取交付事实并写一条新通知;不得转发该报告,也不得逐点压缩它。
回复时用来源路由元数据和 worker 报告;缺技术事实时,等 worker 的报告,或在工单空闲时用 orchestrator_ticket_request_status 去要一份,而不是自己调查。
使用原始的飞书线程;绝不要猜收件人,也不要把私密材料拷进 GitHub。
来源为 GitHub 的工单保持其来源回复路由,除非有明确的飞书目的地。
